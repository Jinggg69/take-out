# 餐饮 SaaS 重构项目 · 均州鱼庄

面向单店及小型连锁餐饮商家的餐饮管理系统，逐步建设多租户、多门店和多种点餐方式支持。

当前以「均州鱼庄」作为管理端和小程序的品牌界面，保留现有 Java 后端与外卖业务基础。新的 Vue 3 管理端已建立，员工、分类、菜品、套餐、订单、工作台与数据统计页面均已接入前端路由和 API 适配。

**当前仍处于单店系统向 SaaS 演进的阶段。多租户、多门店、RBAC、堂食扫码点餐和到店自取尚未实现；前端迁移完成也不等于真实后端联调和部署验收完成。**

## 重构目标

- 多租户、多门店管理，以及数据库、缓存、消息与后台任务的数据隔离。
- 堂食扫码点餐、到店自取、外卖配送三种业务方式。
- 基于 RBAC 的员工操作权限和门店数据范围控制。
- 门店维度的菜品、套餐上下架与可售状态管理。
- Redis 缓存及门店经营数据报表。
- Vue 3 管理端与微信小程序界面重构。

### Vue 3 管理端

当前主要开发入口为 `frontend/junzhou-admin-vue3`。七个业务菜单分别为工作台、数据统计、订单管理、套餐管理、菜品管理、分类管理和员工管理。

迁移沿用现有接口路径和 Token 协议。页面包含加载、空数据、失败和重试反馈；工作台和统计接口未就绪时展示相应状态，不使用模拟经营数据代替接口结果。

管理端保留营业状态、修改密码和 WebSocket 订单提醒入口；这些功能需分别核对真实后端的支持情况，不能仅依据前端按钮或接口定义判断整条链路已可用。

### 后端业务基础

当前后端已具备：

- 员工登录、微信用户登录及 JWT 认证。
- 员工、分类、菜品、口味、套餐和套餐菜品关系管理。
- 基于用户的购物车、地址簿、订单提交与历史查询。
- 下单时的地址归属校验和基于骑行路线的 5 公里配送范围校验。
- 订单与明细写入、清购物车的事务处理。
- 支付预下单、支付通知处理、订单状态流转和退款相关逻辑。
- 菜品与套餐缓存、营业状态、WebSocket 和订单定时任务。

这些实现目前仍以单店为前提。现有订单状态数量统计也不能替代经营报表服务。

### 管理端认证

- 管理端 JWT 使用随机 `jti` 关联 MySQL `admin_session`。每次受保护请求验证签名、有效期、会话和员工启用状态；请求开始及完成时清理 `BaseContext`。
- 退出撤销当前登录会话；禁用账号、修改密码在同一数据库事务中撤销该员工全部会话。重新启用不会恢复旧会话，撤销在事务提交后的下一次认证检查生效。
- 会话签发锁定员工行并重新核对状态和密码快照。会话和撤销状态保存在数据库中；认证查询故障返回 HTTP 503，拒绝访问。
- 不再记录原始密码、微信登录 code 或完整 JWT；敏感对象字段从 `toString()` 排除，员工及认证会话 Mapper 使用 INFO 日志级别。接口 JSON 保持兼容。
- 接口路径和 `token` 请求头沿用原协议。旧版无 `jti` 的管理端 JWT 会返回 401，需要重新登录；Vue 3 管理端改密成功后跳转登录页。

已有数据库升级时，必须先执行 [会话表增量迁移](database/migrations/README.md)，再部署后端。该迁移只新增会话表，不重建业务表。密码仍兼容原项目的 MD5，尚未升级密码哈希算法。

### 下单计价与可售校验

`GET /user/order/quote` 需要用户认证，返回当前购物车的商品明细、商品小计、打包费、配送费与总额。价格、名称和图片读取当前数据库，购物车旧价格与客户端费用不作为计价依据。套餐自身及其组成菜品均需启售，商品缺失或数量异常会拒绝结算。

现行规则为：商品单价 × 购买数量之和，加每份 1 元打包费及每单 6 元配送费；套餐按购买份数计算打包费。后端使用 BigDecimal 精确计价，拒绝异常价格、精度和超出数据库范围的金额。

提交时重新计价，与客户端确认的 `amount` 比较；不一致时不创建订单。实际 `packAmount`、总金额和明细单价由后端写入，已生成订单保留历史快照。小程序进入结算页先获取报价；获取失败禁止提交，提交失败刷新报价后等待用户再次操作，不自动重提订单。

步骤 6 不新增数据库表或列。部署时先发布后端报价接口，再发布小程序；旧后端没有报价接口，新小程序会阻止下单。认证加固所需的会话表迁移仍需按上述说明执行。

### 购物车口味与并发一致性

购物车按当前用户、菜品或套餐类型、商品 ID、口味完整组合识别。同菜不同口味分别计数；空口味统一处理，套餐不区分口味。修改旧同款时合并其重复行并保留总数量，不改其他口味及用户的数据。

加菜、减菜、清空、再来一单和提交订单，在事务的首次业务查询前统一锁定当前用户行。数量通过归属限定的原子 SQL 增减，减到零删除；下单持锁至写订单、明细和清空购物车全部提交，等待中的加菜随后进入新购物车。重购按当前商品信息合并，任一商品失效则整批回滚。

全部应用实例需使用同一套写锁规则。用户行锁按用户划分；本次订单生命周期迁移已补充 shopping_cart.user_id 索引，减少按用户扫描造成的锁等待。直接写数据库的外部程序不受本事务协议保护，购物车 SKU 唯一索引尚未引入。

### 订单超时、提交幂等与支付退款

超过15分钟的待付款且未支付订单通过条件 SQL 取消；并发已支付订单不会被旧扫描结果覆盖。配送中订单仅在已付款、存在实际派送时间且超过1小时后自动完成；历史缺少派送时间的记录跳过。

新订单使用32位随机号，数据库保护订单号、微信交易号和用户请求号的唯一性。新小程序为每次结算生成 clientRequestId；网络或服务端不确定失败后保留原请求内容与请求号，供用户显式重试。服务端按用户串行处理，相同请求返回原订单，改变内容重用请求号会被拒绝；旧客户端不传请求号仍可下单，但没有该幂等保障。

支付与退款通知仅接受POST，先使用指定平台公钥/证书验证原始报文，再解密并核对关联信息。重复支付不重复变更状态或广播；已取消订单迟到支付会持久化同号全额退款意图，保持订单取消。

取消订单与退款请求同事务落库；后台每分钟领取到期请求，在数据库事务外访问微信。PROCESSING保持处理中，仅通知或查询确认SUCCESS才标已退款；超时先查询原退款号，明确不存在才以同号重试。CLOSED/ABNORMAL显示异常并停止自动重试，管理员可调用 `POST /admin/order/{id}/refund/retry` 核查；异常资金处理仍需遵循微信商户流程。历史已标退款记录仅查询核验，不自动重新退款。当前只支持同单全额退款。

上线前必须按 [迁移顺序](database/migrations/README.md) 停止旧实例、升级数据库并切换全部后端。支付配置需包含商户私钥、APIv3密钥，以及平台证书或 `WECHAT_PLATFORM_PUBLIC_KEY_ID`/`WECHAT_PLATFORM_PUBLIC_KEY_FILE_PATH`；退款通知指向 `/notify/refundSuccess`，支付通知指向 `/notify/paySuccess`。`PAYMENT_JOBS_ENABLED=false` 可暂停支付核查和退款恢复任务，不会关闭原有订单超时任务。缺少商户配置时不执行恢复任务；缺少有效验签配置时通知失败关闭。

## 本地开发

以下命令以仓库根目录为起点，每组命令在独立终端中执行。启动前需要准备本地配置和外部服务；详细命令与已执行范围见 [本地开发说明](docs/stage1/development.md) 和 [验证记录](docs/stage1/verification.md)。

### 1. 准备环境与数据库

- 安装 JDK、Maven 和 MySQL；本机已验证版本见上述说明。
- 新管理端要求 Node.js `>=22.18.0`，具体依赖以其 `package.json` 和锁文件为准。
- 准备 Redis；小程序使用 HBuilderX 与微信开发者工具。
- 支付、图片上传和配送范围校验分别需要微信支付、OSS、百度地图配置。

`database/junzhou.sql` 创建并使用 `sky_take_out` 数据库，包含 `DROP TABLE IF EXISTS`。仅在确认可重建的开发库中初始化；已有数据的数据库需要备份和增量迁移，不能直接执行该脚本升级。

已有库按迁移说明依次执行 `database/migrations/20261026_01_admin_session.sql`、`database/migrations/20261027_01_order_payment_lifecycle.sql`，再发布新后端。全新初始化脚本已包含会话表、订单生命周期字段及退款表。

### 3. 启动 Redis 和后端

已准备仓库配套的本地 Redis 时，可在根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\redis.ps1 start
powershell -ExecutionPolicy Bypass -File .\scripts\redis.ps1 status
```

该脚本依赖被忽略的本地 Redis 安装，并非全新检出后的自动安装器。也可以使用自行安装的 Redis，保持连接配置一致。

在仓库根目录运行后端检查与启动命令。JWT 密钥需要先通过环境或自己的外部配置提供：

```powershell
.\scripts\backend.ps1 -Goal package
java -jar backend/junzhou-take-out/junzhou-server/target/junzhou-server-1.0-SNAPSHOT.jar --spring.config.additional-location=optional:file:backend/junzhou-take-out/junzhou-server/src/main/resources/
```

默认端口为 `8080`，Knife4j 接口文档入口为 `http://localhost:8080/doc.html`。上述构建入口会运行测试；已有缓存且不需下载时可追加 `-Offline`。它支持 PATH、MAVEN_HOME、IntelliJ 自带 Maven 或显式 `-MavenPath`，详见开发说明。

### 4. 启动 Vue 3 管理端

```powershell
cd frontend/junzhou-admin-vue3
npm ci
npm run dev
```

开发地址为 `http://127.0.0.1:8889/`，端口被占用时直接报错。

开发服务器默认把 `/api/employee/login` 转发到 `http://localhost:8080/admin/employee/login`。`API_PROXY_TARGET` 可覆盖 API 代理目标；`/ws` 代理保持 WebSocket 路径，不增加 `/admin` 前缀。Socket 实际使用的地址同时取决于前端模式配置。

`VITE_*` 变量会进入浏览器资源，只能保存可公开配置。个人环境覆盖使用被忽略的 `.env.development.local` 等文件。

### 5. 运行小程序

1. 使用 HBuilderX 打开 `weixin-uniapp`。
2. 在小程序配置中设置自己的 AppID，并与后端微信应用配置保持一致。
3. 在 `weixin-uniapp/utils/env.js` 设置 API 地址，当前源码默认 `http://localhost:8080`。
4. 使用微信开发者工具运行，并按实际环境配置请求域名及相关能力。

真机不能通过 `localhost` 访问开发电脑，需要改用设备可访问的后端地址。当前小程序仍使用 Vue 2，不能按新管理端的 Vite 工程方式启动。

### Nginx 是否必需

本地使用 Vite 开发管理端、Spring Boot 提供接口时，不要求启动 Nginx。小程序也可以直接请求后端。

仓库不再包含 Nginx 程序、配置及旧管理端静态资源。新管理端构建产物需要部署到实际的静态资源目录；部署入口需将 `/api/` 转发至后端 `/admin/`，并按需代理 `/user/` 和 `/ws/`。

生产环境可以使用 Nginx 或其他部署入口处理静态资源、HTTPS 和请求转发。租户识别、RBAC 和数据隔离仍由后端负责。

## 当前已知缺口

后续重构需要先处理以下源码中可确认的问题：

- 数据表与业务查询没有租户、门店边界；分类、菜品、套餐名称和员工用户名仍使用全局唯一约束。
- 购物车已有口味区分、用户索引和事务并发保护，仍需 SKU 数据库唯一约束及未来门店边界。
- 支付退款尚需真实商户、真机、通知公网接入和历史资金对账验收。
- 用户催单 Controller 当前只返回成功，未调用催单业务；已有 WebSocket 采用全局连接广播，未按门店隔离。
- `/workspace/*`、`/report/*` 的前端适配已存在，但相应后端接口尚待补齐；小程序商户信息等缺口仍需专项处理。
- 小程序中的桌台接口定义和店铺字段不代表已经实现堂食或多门店业务。

上述问题需要专项验证和修复后再扩大业务范围。实际运行库是否与 `junzhou.sql` 一致，也需要在迁移前核对。

## 分阶段重构计划

阶段 1 的代码与本地验收已有实现；真实商户及部署验收完成后再扩大业务边界。阶段2及以后为后续计划。

| 阶段 | 依赖 | 主要工作 |
| --- | --- | --- |
| 1. 稳定单店基线 | 当前代码分析 | 统一构建配置，核对真实数据库与接口，修正金额、归属、购物车、超时任务及支付退款问题，完成真实联调 |
| 2. 租户与门店基础 | 阶段 1 | 明确账号与商户关系，建立租户、门店和请求上下文；回填旧数据，覆盖 SQL、缓存、消息、通知与任务隔离 |
| 3. 员工与 RBAC | 阶段 2 | 建立门店任职、角色权限、数据范围及门店切换；由后端执行授权 |
| 4. 门店菜单与购物车 | 阶段 2、3 | 建立租户目录与门店销售关系，统一菜品和套餐可售判断，拆分门店购物车及缓存 |
| 5. 三种点餐方式 | 阶段 4 | 服务端报价和订单快照、幂等提交；堂食桌台或桌次、自取凭证、门店配送、支付退款闭环 |
| 6. 经营报表 | 阶段 3、5 | 定义营业额、退款、有效订单、销量口径，实现门店报表、授权汇总与导出 |
| 7. SaaS 界面与发布验证 | 对应接口逐步稳定 | 在现有 Vue 3 工程上增加 SaaS 能力，继续重构小程序，完成端到端验证和数据库迁移演练 |

优先沿用当前单体应用逐步拆分业务边界。租户数据隔离应覆盖读取、写入、关联表、批量操作、缓存与消息，不能仅通过列表参数或隐藏菜单实现。
