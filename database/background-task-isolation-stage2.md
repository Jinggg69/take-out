# 阶段 2.5：后台任务隔离

2026-11-03，基于 HEAD `3d44c53` 的工作区增量。本项完成逐订单任务范围，未开放真实多租户业务；2.5 的文件归属仍待完成，支付账户路由仍属于 2.6。

## 扫描与执行

`OrderTask` 不再建立默认租户 1 / 门店 1 的过渡作用域。后台入口先清理线程身份与范围，通过 `BackgroundJobScope.scan` 显式开启候选扫描；Mapper 在没有扫描标志或仍存在请求作用域时拒绝全局扫描。扫描只返回订单 ID 和数据库归属，退款扫描额外返回稳定退款号；不提供无范围业务读写入口。

候选查询关联租户、门店核验归属，跳过缺失父记录或租户/门店不一致的订单；每批最多 100 项，按订单 ID 游标翻页。扫描不按租户/门店启停状态过滤，以便停用商户的历史交易仍能完成订单维护。单笔失败记录订单 ID，继续后续订单；扫描本身失败则结束该类任务，下次调度重试。

每笔候选处理前检查有效 ID，再建立候选归属的 system RequestScope。订单超时和配送完成更新同时匹配订单 ID、租户、门店以及原状态、支付状态、时间边界和门店归属。扫描后归属变化或状态变化不会被旧候选覆盖。原 15 分钟/1 小时严格边界、配送出发时间和条件更新语义保留。

每笔处理和任务退出均在 finally 清理 RequestScope 与 BaseContext，不继承上一笔订单、请求或线程池残留身份。

## 支付恢复边界

`PaymentRecoveryTask` 使用同样的候选扫描和逐订单范围。退款候选跳过有效租约，随后仍通过原 `claim` 事务竞争行锁和租约；退款号、2 分钟租约、尝试次数、退避和租约 token 校验逻辑均未修改。支付核验新增逐订单入口，重新读取当前范围订单并核验取消/未支付、非终态及重试间隔，避免信任扫描快照。

支付仍只有一套微信商户配置，因此保留调度入口及每笔处理前的 `requireLegacySingleStore`，并拒绝非默认租户/门店候选。禁用任务或未配置商户号时直接退出且清理上下文。多租户数据库中的支付恢复继续拒绝执行，避免以默认支付账户处理其他租户历史资金；2.6 完成订单支付账户绑定和路由后再移除该保护。普通订单超时/配送维护已可在隔离测试中跨租户执行。

现有请求内的退款重试和受控支付回调继续使用原入口；本项未改变回调验签、退款金额验证或支付幂等规则，无 schema 迁移。
