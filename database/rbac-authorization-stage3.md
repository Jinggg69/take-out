# 阶段 3.3：后端鉴权、撤权与管理员保护

## 已接入的行为

管理端拦截顺序为 JWT/持久化会话认证 → 员工租户和门店范围 → 具体动作授权。除登录外，每个管理端处理方法必须声明 `RequireActions`；缺失声明默认 403。只有退出和修改自己密码使用空动作列表，并建立独立身份上下文，不要求员工具有业务门店。认证失败返回 401，授权失败 403，拦截阶段存储不可用 503。

角色权限每次从数据库读取，不缓存。订单、店铺等操作只使用已授权的当前门店；沿用阶段二 Mapper 的 tenant_id/store_id 条件，伪造其他门店的订单 ID、关联 ID 和批量 ID 不会扩大范围。具有租户全部店范围也仍然一次操作所选门店，不自动汇总所有门店数据；跨店报表在阶段六提供。

`X-Store-Id` 必须是后端核验的允许门店。只有一个可访问门店时可省略，多店必须明确选择；前端门店切换将在 3.4 实现。无任何业务授权的员工不能访问业务接口，但仍可退出/改密。

权限策略包括：接单要求 order:accept；退款重试要求 order:refund；拒单和取消同时要求对应动作与 order:refund，避免通过自动退款路径绕过财务权限。店员无退款/导出授权时直接 HTTP 请求同样拒绝。报表导出接口尚未建设，不提供绕过授权的替代入口。

菜品、分类、套餐基础目录以及员工资料属于整个租户。共享目录写操作和员工资料操作要求该具体动作具有 TENANT_STORES 范围，防止本店员工修改其他门店共用资源；目录读取仍按租户隔离。门店商品菜单管理在阶段四实现。分类启停沿用 category:update。上传要求 file:upload；已上传目录文件信息读取要求 dish:read，仍保留文件服务原有归属核验。

## 本店和指定店均按角色任职隔离

3.2 的 employee_role_store 现在同时用于 CURRENT_STORE 与 SPECIFIED_STORES。本店要求所选门店在该角色的任职清单中；指定店允许清单内任一所选门店。二者均不能借用另一角色的清单。TENANT_STORES 不依赖任职清单，仍只能访问员工所属租户的有效门店。

与 3.2 纯模型阶段相比，这是对 CURRENT_STORE 的进一步收紧：仅有 employee_store 总任职记录不足以启用角色业务权限，必须明确配置 employee_role_store。不会自动将员工全部门店复制给每一个角色。新授权入口会维护总任职和角色任职的复合外键关系。

## 授权变更入口

均要求当前员工拥有 TENANT_STORES 范围的 employee:manage。tenant_id 从已认证上下文获取，前端不能指定。接口为整体替换，调用方需提交完整目标清单：

- `PUT /admin/rbac/roles/{role}/permissions`，请求体为具体动作字符串数组，例如 `["order:read","order:accept"]`。未知动作、未知角色拒绝，空数组表示撤销该角色全部权限。
- `PUT /admin/rbac/employees/{employee}/assignments`，请求体为角色任职数组，例如 `[{"roleCode":"CLERK","dataScope":"CURRENT_STORE","storeIds":[10]}]`。所有门店必须有效且属于当前租户；重复角色拒绝。空数组表示撤销目标员工全部角色与门店任职。TENANT_STORES 可提供空门店集合。

权限和任职变更在同一事务保守撤销当前租户所有管理会话，包括操作者，其他租户不受影响；成功后必须重新登录。停职和改密沿用撤销目标员工全部会话。SQL 写语句本身也必须具备已验证员工上下文，不能通过直接调用新 Mapper 绕过租户边界。

WebSocket 握手及每次发送消息前均重查会话、当前门店范围和 order:read。撤权后旧连接不再接收消息，并在下一次校验时关闭；没有消息时不承诺立即主动断开空闲连接。已经通过鉴权并开始执行的请求，不承诺被后续撤权追溯中断。

## 最后一名管理员与并发

有效商户管理员定义为：员工启用，具有 MERCHANT_ADMIN 角色、TENANT_STORES 范围和 employee:manage 动作。授权变更、角色权限变更、员工启停统一先锁当前有效 tenant 行，再在事务中修改，最后重新核对至少保留一名有效管理员。删除最后一名管理员的角色、收窄其范围、移除其授权管理权限或停职均会回滚；两个管理员并发撤权也不会清空管理员。

登录签发会话同样先锁 tenant，再锁凭据验证后的 employee，避免授权变更撤销会话期间旧登录流程随后插入会话。账号状态和租户归属在锁内重验。

## 部署和回退

先执行 3.1、3.2 迁移。本步骤无新增数据库表或列。实际应用库尚未执行任何迁移或授权写入。

在维护窗口逐租户核对并明确引导至少一名有效管理员：员工启用，员工角色 MERCHANT_ADMIN 的 data_scope 明确设为 TENANT_STORES，且角色含 employee:manage。3.1/3.2 脚本不会猜测管理员或自动提升现有范围。CURRENT_STORE/SPECIFIED_STORES 员工还需显式核对该角色的 employee_role_store 清单。未完成引导时接口将拒绝业务访问。

原模板只含初始动作，并不自动获得后来增加的 create/delete/status/file:upload 等动作；用经核对的完整动作数组显式配置。不得为部署方便无条件恢复运营中撤销的权限。建议先引导管理员，再通过新接口配置角色和员工任职，重新登录验收。

数据库角色和任职关系的运行期写入必须经新服务；DBA 直接 SQL 不自动撤销会话，也不提供最后管理员事务保护。如需人工修复，停写并明确撤销相关租户会话。新增员工默认无角色，等待明确授权。管理端接口已支持多店选择，用户端仍保留阶段二单店过渡门禁，待阶段四完成用户选店和门店菜单后开放。

所有实例须一起升级，旧实例不会执行本阶段动作授权。回退前停写并评估权限差异，保留全部授权数据；不要把旧应用恢复当作安全的权限回退。未进行发布、推送或提交。

## 执行与验证记录

采用测试驱动，先验证模型/接口不存在的失败，再实现。独立审查发现身份自服务错误依赖门店、本店角色借用其他角色门店，分别添加失败回归并修复；最后管理员与并发撤权有真实数据库事务测试。原有仅测试身份认证/业务流程的 MVC 夹具显式隔离新增鉴权依赖，新 RBAC 集成测试独立覆盖真实鉴权，不依赖这些夹具。

主要测试：RbacAuthorizationTest、RbacIntegrationTest、RequestScopeMvcTest、RequestScopeInterceptorTest、AdminAuthenticationTest、EmployeeStatusTest、EmployeePasswordTest、OrderSocketIsolationTest、OwnershipWriteGuardTest。验证覆盖所有管理端方法必须声明策略、店员 HTTP 退款/取消拒绝、未知方法默认拒绝、跨租户和跨店拒绝、撤权后重新读取权限、租户会话撤销边界、最后管理员变更和停职回滚、两个管理员并发撤权。

最终验证：`./scripts/backend.ps1 -Offline` 全量 353 项，0 失败、0 错误、1 跳过，BUILD SUCCESS；`git diff --check` 通过。测试需要本机 Redis 与 HTTP 测试端口，按原状态临时启动/恢复 Redis。

阶段 3.4 已增加管理端角色任职与门店切换，以及门店上下文/授权配置读取接口，使用和验证见 [管理端说明](rbac-admin-stage3.md)。
